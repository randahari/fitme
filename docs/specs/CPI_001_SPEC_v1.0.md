# 1. Status / Scope

**Status: SPEC — awaiting Engineering Readiness sign-off and Work Package implementation. Not implemented.**

Scope: a narrow, domain-agnostic capability that lets an **explicit, first-person** preference statement typed into the Coach Conversation Surface become a durable, user-visible, user-editable/rejectable Typed Memory record — and produces a governed, natural acknowledgment when it does. CPI-001 reuses the existing Typed Memory store (`js/memory.js`), the existing D6 transparency surface, the existing CCC-001 conversation turn (`CurrentUserTurn`), and the existing Coach Decision System pipeline (Stage 1-10) unmodified in shape, adding only the specific, disclosed extension points listed in §14/§15/§25.

CPI-001 is **not** a reopening of the paused Preference V1 initiative (Roadmap.md: "Preference V1 remains paused"), not a new memory architecture, and not a general Natural User Understanding capability. It is a single, narrow vertical — structurally the same kind of "first vertical" DUC-001/TRR-001/USM-001 each already were for their own capability.

# 2. Product Problem

FITME can already persist and display conversation turns (CCC-001) and already has a durable, user-editable Typed Memory store consumed by Coach reasoning (USM-001/TRR-001), but nothing connects the two: a bare, explicit preference statement typed into the Coach Conversation Surface today produces `TerminalDecision.kind:'SILENCE'`, is never written to Typed Memory, and receives no acknowledgment at all — the pending bubble is silently removed (`js/ui/coachConversationPresenter.js` `renderNoResponse()`). CPI-001 closes this specific gap for a bounded class of explicit statements, without building a new memory system and without persisting or acknowledging anything the user did not explicitly declare.

# 3. User Experience Contract

- The user types an explicit first-person preference statement (§8) into the existing Coach Conversation Surface.
- If the statement is in V1 scope, literally anchored to the user's own words, non-Safety, and `memoryConsent.granted === true`: FITME persists it as a durable, active Typed Memory record. The turn's one final response always represents that capture — either as a short, standalone, governed acknowledgment (the ordinary case, when nothing else needed saying this turn) or, when the same turn also carries a real primary professional/Safety response, as a brief, secondary acknowledgment woven into that SAME single response, never as a second message and never overriding the primary content's own priority (wording owned entirely by Expression in both shapes — §13/§14/§15). A reactivation of a previously rejected preference (§12) always includes a distinct, mandatory reactivation acknowledgment, even when a primary response also exists that turn.
- If `memoryConsent.granted` is `false`: no durable write occurs; the conversation turn itself is still persisted and understood as an ordinary conversational turn (CCC-001 unchanged); no acknowledgment implying "I will remember this" is ever rendered (§16).
- If the statement is ambiguous, out of V1 scope, or Safety-relevant: no durable write occurs, and the turn's outcome falls back to existing, already-governed behavior (§16/§17) — never a fabricated acknowledgment.
- The user never sees an interrupting confirmation dialog for an eligible, successfully-captured preference (Product Decision 18). Their only ongoing control surface is the existing D6 "🧠 מה המאמן יודע עליי" sheet — unchanged, already supports view/confirm/edit/reject/delete (§19).
- No new UI surface is introduced.

# 4. In Scope / Out of Scope

**In scope (V1):**
- Detection, deterministic validation, and durable persistence of an **explicit, first-person** preference statement in exactly the three closed classes of §8.
- A new, governed acknowledgment outcome, Expression-rendered.
- Deterministic dedup/update-in-place for a restated or contradicted preference (§12).
- Reuse of the existing D6 transparency surface for visibility/correction (§19).

**Out of scope (V1 — explicit, per approved Product decisions):**
- Behavior-inferred preferences (no explicit statement) — Product Decision 13. No `candidate`/`inferred_*` producer is built by this Item.
- Safety/medical statements (e.g. "הרופא אמר לי לא לרוץ") — Product Decision 14; remains USC-001/USP-001/CSR-001's exclusive domain, untouched.
- Habit/routine/frequency statements (e.g. "בדרך כלל אני מתאמן שלוש פעמים בשבוע") — explicitly named by Product as closer to a fact/habit than a preference; not forced into this path.
- Goals, unless already covered by another authoritative path (none is touched here).
- Food preferences, coaching-style preferences, life events, travel context — reserved for a future, separate vertical using the same domain-agnostic foundation (§20).
- Reopening Preference V1, any new memory architecture, embeddings, vector search, summarization, transcript mining, provider-side memory, raw Claude → UI, raw Claude → Firestore.

# 5. Authority Model

Governed entirely by REM-003 (`APPROVED / IMPLEMENTED`, production-wired as `js/authorityContract.js`) and B1 §10-§11 (both cited as binding precedent by the closed USM-001 SPEC):

- **Path A — Explicit User Declaration** (REM-003 §5): *"הצהרת משתמש מפורשת שעוברת Validation, Business Rules ואישור לפי הצורך"* — the only path CPI-001 uses. Every statement this Item persists is, by construction (§9/§10), the user's own explicit, first-person declaration.
- **Authoritative Write Contract** (REM-003 §9): `Input → LLM (Optional) → Validation → Business Rules → Deterministic Decision → Persistence Layer → Firestore`. CPI-001's pipeline is exactly this shape (§14): an AI interpreter (optional, advisory) produces a structured reading; a deterministic gate (§10) validates it; a deterministic decision persists it via the existing Persistence Layer (`js/memory.js`).
- **Forbidden paths** (REM-003 §10) — `LLM → Firestore` and `LLM → Coach Memory` directly — are never used. The interpreter never writes; only the deterministic gate's own decision, executed by existing `js/memory.js` API calls, writes.
- **B1 §10**: *"An LLM MAY propose a candidate memory... No LLM SHALL directly create authoritative canonical memory."* CPI-001 does not use `candidate` at all (Product Decision 12) precisely because Path A already supplies direct authoritative status once validated — this is not a violation of B1 §10, it is B1 §10's own alternate path (Path A vs. the LLM-proposal-then-promotion path), exactly as USM_001_SPEC's own precedent states: *"a `status:'active'` user-stated fact is already, structurally, a Path-A Authoritative Fact, not an Observation requiring accumulation."*
- **status:'candidate' remains untouched and available** for a future inferred/proposed-memory Work Item (Product Decision 12) — CPI-001 introduces no producer of `candidate`-status records.

# 6. Source vs Interpretation Authority

Never collapsed, per Product Decision 8:

- **Statement Authority** — the persisted Typed Memory record itself: `source:'user_stated'`. This describes *whose declaration the assertion is* (the user's), not which code executed the Firestore write — supported directly by REM-003's own Guiding Principle: *"מקור הסמכות נקבע לפי סוג המידע, לא לפי מקור ההגעה שלו... המשתמש הוא מקור הסמכות לפרטים האישיים, יעדים והעדפות."*
- **Interpretation Authority** — the AI interpreter's structured reading (`preferenceClass`, `polarity`, `target`) never itself becomes the authoritative record; it is the *input* to a deterministic validation step (§10) that must independently re-verify the reading is literally anchored in the user's own current-turn words before anything is persisted. This mirrors `ActivityPreferenceInterpreter`/`ActivityOppositionInterpreter`'s own established `interpretationAuthority:'DERIVED_INTERPRETATION'` discipline exactly (`js/coachDecisionSystem/activityPreferenceInterpreter.js` header: *"Statement Authority != Interpretation Authority is preserved by construction"*).
- No new `source` enum value is introduced (repository evidence in the prior investigation showed this would be invisible to every existing consumer filter and requires no `firestore.rules` change to reuse `'user_stated'`).

# 7. memoryConsent Contract

- **Existing, unmodified, global semantics preserved**: `memoryConsent.granted` continues to gate exactly what it already gates — **reading** Typed Memory for Coach reasoning (`js/stateAccess.js` `readUserStatedMemory()`), and nothing else. The manual D6 "add fact"/edit/reject/delete paths remain entirely unaffected by this SPEC (Product's own instruction: "Do NOT change the global historical meaning of memoryConsent for unrelated manual-memory paths unless strictly required" — not required here).
- **New, additive rule scoped to this Item only**: for the conversational intake path specifically, `memoryConsent.granted === true` is also required **before persistence**, not only before consumption. If consent is absent/false at the moment an otherwise-eligible statement is detected:
  - No Typed Memory write occurs (not even as `candidate` — Product Decision 12 forecloses that route anyway).
  - The turn is still persisted and rendered as an ordinary conversational turn via the existing, unmodified CCC-001 lifecycle (`PENDING`/`SILENCE` per the existing rules) — this Item never blocks or alters ordinary conversation persistence.
  - No acknowledgment implying durable capture is ever rendered (§16, Scenario 2).
- **New read requirement**: the deterministic gate (§10) needs a plain boolean read of `memoryConsent.granted` from inside the governed pipeline. No existing StateAccess capability exposes this as a standalone read (`readUserStatedMemory()` only uses it internally as a pre-fetch gate, never returning it). §14 defines a new, narrow, sibling StateAccess capability for this, mirroring CCC-001's own precedent of adding a sibling identity under the same `memoryLayer` engine rather than widening an existing one.

# 8. V1 Preference Vocabulary

Closed, structured, and extensible by **class registration**, never an unconstrained dump. Three classes in V1, matching Product's named examples exactly:

| Class | Examples | Target vocabulary | Polarity vocabulary |
|---|---|---|---|
| `ACTIVITY_SENTIMENT` | "אני לא אוהב לרוץ", "אני אוהב שחייה" | **Literal, bounded, substring-anchored text** (max 80 chars), copied verbatim from the user's own words — reusing `ActivityPreferenceInterpreter`'s own established precedent exactly (it does not force activity names onto MAI-001's closed 6-token vocabulary either, since that would silently reject real statements about non-enumerated activities, e.g. Pilates) | `POSITIVE` \| `NEGATIVE` (reuses `ActivityPreferenceInterpreter.POSITIVE_SENTIMENT`/`NEGATIVE_SENTIMENT` vocabulary by pattern) |
| `TRAINING_TIME_PREFERENCE` | "אני מעדיף להתאמן בערב", "אני אוהב להתאמן בבוקר" | Closed token: `MORNING` \| `AFTERNOON` \| `EVENING` \| `NIGHT` (new, narrow, V1-defined enum — no existing repository vocabulary covers time-of-day) | `POSITIVE` \| `NEGATIVE` |
| `TRAINING_FORMAT_PREFERENCE` | "אני מעדיף אימונים קצרים", "אני אוהב אימונים ארוכים" | Closed token: `SHORT` \| `LONG` (new, narrow, V1-defined enum, deliberately limited to duration only — intensity/type/other format dimensions are out of scope for V1) | `POSITIVE` \| `NEGATIVE` |

What is closed: the **class enum** (exactly 3 values in V1, extensible only by a future SPEC amendment — §20), the **polarity enum** (2 values), and the **target enum** for classes B/C. What remains literal, bounded text: only the class-A activity name itself, by deliberate reuse of already-approved precedent rather than inventing a stricter constraint the existing interpreter family does not itself apply.

**Known, disclosed V1 limitation**: literal-anchored activity text means "ריצה", "לרוץ", and "running" would be treated as three distinct targets (three distinct deterministic identities, §12) rather than normalized to one semantic activity. This is the same limitation already accepted for `ActivityPreferenceInterpreter`'s own `activityText` field; solving it would require a semantic-normalization capability this Item deliberately does not build (out of scope — would risk exactly the "large new architecture" Product asked to avoid).

# 9. Detection / Interpretation Contract

New component: **`ExplicitPreferenceStatementInterpreter`** (`js/coachDecisionSystem/`), structurally identical in skeleton to `ActivityPreferenceInterpreter`/`ActivityOppositionInterpreter` (single-turn batch shape, `configure({callClaude})`, fixed timeout, no retry, literal-substring enforcement, fail-closed).

- **Input**: exactly one `CurrentUserTurn` (§02 shape, per DUC-001), never conversation history as a source of facts — `recentConversationContext` may be threaded in as an **additive, optional** parameter for reference resolution only (pronouns, "גם את זה"), mirroring `TurnUnderstandingInterpreter.classify(turn, recentConversationContext)`'s own established, structurally-enforced discipline (its own header: never a source of facts, only for resolving what the current turn refers to).
- **Output** (closed, four fields, all-or-nothing per turn):
  ```
  {
    eligible: true|false,
    preferenceClass: 'ACTIVITY_SENTIMENT'|'TRAINING_TIME_PREFERENCE'|'TRAINING_FORMAT_PREFERENCE'|null,
    polarity: 'POSITIVE'|'NEGATIVE'|null,
    target: <string>|null,          // literal text (class A) or closed token (class B/C)
    ineligibleReason: 'NO_EXPLICIT_PREFERENCE'|'SAFETY_EXCLUDED'|'AMBIGUOUS'|'OUT_OF_V1_SCOPE'|null
  }
  ```
- **Prompt discipline, mirroring `ActivityOppositionInterpreter`'s own established Safety-exclusion pattern verbatim**: the classifier is explicitly instructed to answer `ineligibleReason:'SAFETY_EXCLUDED'` for anything resembling a medical/practitioner-sourced restriction ("הרופא אמר לי..."), never attempting to double-classify Safety content as an ordinary preference — this interpreter never competes with or duplicates `SafetyContextInterpreter`/`UserSafetyProvenanceInterpreter`'s own authority (§17).
- The classifier is likewise instructed to answer `ineligibleReason:'OUT_OF_V1_SCOPE'` for a habit/frequency/routine statement (e.g. "בדרך כלל אני מתאמן שלוש פעמים בשבוע") and for any statement not literally a first-person, present-tense sentiment/preference declaration — never guessing a class for an ambiguous or borderline statement (`ineligibleReason:'AMBIGUOUS'`).
- **Literal anchoring** (Product Decision 10): identical, independently-implemented `isLiteralSubstringOf()` discipline to `ActivityPreferenceInterpreter`/`ActivityOppositionInterpreter`/`SafetyContextInterpreter` — `target` (class A) must be a literal substring of the turn's own text; a result failing this check is rejected by `parseAndValidate()`, never persisted as a paraphrase or inference.
- **Never gated on, and never gates,** `ConversationalNeedCreator`'s own Need recognition — this interpreter runs unconditionally on every `DIRECT_TURN_PASS` turn, in parallel with `TurnUnderstandingInterpreter`, exactly as Product's own examples establish (a bare preference statement is never a request).
- **`ineligibleReason:'SAFETY_EXCLUDED'` from this interpreter is a first-line, advisory-only signal, never the authoritative Safety boundary.** It is cheap, prompt-level self-exclusion that reduces obviously-wrong cases early, but a misclassification here (the interpreter incorrectly returning `eligible:true` for a Safety-relevant statement) does not, by itself, authorize anything — §10's own independent, mandatory Safety veto never trusts this interpreter's own Safety judgment and is required regardless of what this interpreter concluded.

# 10. Deterministic Validation Contract

New component: a small, deterministic gate (mirrors `EligibilityEvaluator`'s/`EvidenceEvaluator`'s shape — pure function plus one independent, reused classifier call, no side effects, no Firestore write), invoked only when the interpreter (§9) returns `eligible:true`. This is REM-003 §9's own "Validation → Business Rules → Deterministic Decision" link in the Authoritative Write Contract, and it produces exactly one thing: a **Preference Intake Authorization** — never a TerminalDecision, never a Firestore write, never an Expression invocation (§13/§14).

Checks, all required (fail-closed — any failure yields `authorized:false`, never a partial write):
1. `preferenceClass` ∈ the closed §8 enum, `polarity` ∈ `{POSITIVE, NEGATIVE}`, and (for classes B/C) `target` ∈ that class's closed token enum — malformed interpreter output is never trusted structurally, mirroring every sibling interpreter's own `parseAndValidate()` discipline.
2. `target` (class A only) passes `isLiteralSubstringOf()` against the turn's own text — re-verified here, never merely trusted from the interpreter (defense in depth, matching `SafetyContextInterpreter`'s own established literal-substring re-enforcement pattern).
3. `memoryConsent.granted === true` (§7) — read via the new StateAccess capability (§14).
4. The turn does not already carry `negativeControlPresent:true`/an active professional-capability Candidate this cycle in a way that would conflict (§14 priority rule) — this is a sequencing rule, not a rejection; both may coexist (§14).
5. **Independent Safety veto — resolves Issue 2 (Canonical Review): §9's own `SAFETY_EXCLUDED` self-exclusion is never, by itself, sufficient to authorize an authoritative write.** Before authorization, the gate REQUIRES a separate, independent classification of the SAME current-turn text by the **existing, unmodified, already-production-wired `SafetyContextInterpreter` (USC-001)** — not a new Safety architecture, the exact same collaborator `memoryLayer.js`'s own `userSafetyContext` step already uses for durable memory, additively handed one more record: `[{id:'turn:'+turnId, text: turn.text}]`, mirroring byte-for-byte the established `'turn:' + turnId` convention `explicitRequestControls`/`readinessStateContext` already use to additively submit the current turn to a sibling interpreter (`memoryLayer.js:379-381,546-549`). `SafetyContextInterpreter` is already `configure()`d in production (`js/app.js:325`) — zero new wiring is required for the interpreter itself, only the new call site inside this gate.
   - If this independent classification returns **any** restriction for this turn (`restrictions.length > 0`), the gate returns `authorized:false, reason:'SAFETY_VETO'` **unconditionally — regardless of what `ExplicitPreferenceStatementInterpreter` (§9) itself concluded.** This is the fail-closed property Issue 2 requires: a misclassification by the preference interpreter alone can never authorize a write, because a second, independently-invoked, independently-prompted classifier must also find nothing.
   - **Safety classifier failure MUST fail closed — resolves the Canonical Review's Safety fail-closed clarification.** `SafetyContextInterpreter.classify()` itself (§7/§12 of USC-001) is, by its own documented, closed-foundation contract, deliberately **fail-closed-by-omission toward its own existing durable-memory consumer**: a thrown error, a timeout, or malformed/unparseable model output all degrade internally to the *same* empty/partial `results[]` a genuine, confident "no restriction found" classification would also produce — `classify()` exposes no field distinguishing the two. That collapse is a correct, accepted, disclosed design choice for `userSafetyContext`'s own non-authoritative, advisory Reasoning-Context role (graceful degradation, D3 §12.3) — but it is **not acceptable** as the sole signal gating an authoritative Typed Memory write, where "the check could not be trusted this call" and "the check ran and confidently found nothing" must never be treated identically. This gate therefore requires a second, small, **purely additive** export from `safetyContextInterpreter.js` — `classifyWithStatus(records)`, returning `{status:'CLASSIFIED'|'FAILED', restrictions:[...]}` — reusing 100% of that file's own existing, unmodified internal `partitionIntoBatches()`/`classifyBatch()`/`parseAndValidate()` machinery and surfacing the `status` those functions already internally compute (timeout/thrown/malformed) but currently discard before returning. This is the exact, already-approved precedent `TurnUnderstandingInterpreter` itself established for the identical class of problem (its own `interpretationStatus: 'CLASSIFIED'|'FAILED'`, Blocker 7) — reused by pattern, not merged or imported. **`classify()` itself, its existing return contract, and its existing sole caller (`memoryLayer.js`'s `userSafetyContext` step) are untouched, unchanged, and byte-identical** — this is a narrow, additive, backward-compatible sibling export, never a redesign of USC-001's own closed behavior. If `classifyWithStatus()` returns `status:'FAILED'` (or, defensively, throws or fails to resolve at all — never expected, kept only for the same "never trust an upstream guarantee alone" discipline this repository already applies everywhere else), the gate returns `authorized:false, reason:'SAFETY_VETO_UNAVAILABLE'` — **never** interpreted as, or coerced into, "zero restrictions found." No write, no Pass 2, no acknowledgment (§16, new Scenario 9).
   - **Secondary, zero-cost defense-in-depth layer**: the gate additionally cross-checks `target` (class A) against `pipelineContext.userSafetyContext.items[].restrictedActivityText` (already assembled once per Decision Pass — no additional read or AI call) — a literal-substring/case-insensitive match against any EXISTING durable Safety restriction also vetoes authorization (`reason:'SAFETY_VETO_DURABLE'`), catching the case where an earlier turn already established a durable restriction on the same target even if the current turn's own wording doesn't repeat it. This secondary layer inherits `pipelineContext.userSafetyContext`'s own existing `availability` flag, which carries the same "available-if-attempted, not available-if-attempted-and-confidently-empty" limitation described above — it is explicitly a best-effort, non-primary layer; the `classifyWithStatus()` current-turn check above is the sole primary, authoritative fail-closed guarantee.
   - This veto is strictly a **read-only, non-persisted refusal signal** — it never creates Safety Context, never writes anything, never diagnoses, never routes the statement to a new or existing Safety capability, and never substitutes for Friends Alpha Item 6 (bare-statement Safety intake, still NOT STARTED, still untouched). A vetoed statement's Safety content is not captured anywhere by this Item — it is left exactly as unrecognized as it is today (§17).

Output: a frozen, closed **Preference Intake Authorization** object:
```
{
  authorized: true|false,
  reason: 'OK'|'INVALID_SHAPE'|'LITERAL_ANCHOR_FAILED'|'CONSENT_ABSENT'|'SAFETY_VETO'|'SAFETY_VETO_DURABLE'|'SAFETY_VETO_UNAVAILABLE',
  candidateRecord: {preferenceClass, polarity, target, sourceTurnId} | null
}
```
This object authorizes a write; it never performs one, and it never claims — implicitly or explicitly — that anything has been remembered (§13/§14).

# 11. Typed Memory Persistence Contract

- **Schema**: unchanged. `type:'preference'` (already in `MEMORY_TYPES`, `js/memory.js:29` — schema-recognized since USM-001, previously disclosed as having "no live producer yet," RG-1). This Item is that producer.
- **Record shape** (payload deliberately reuses the existing `{key, value}` shape already rendered correctly, with zero changes, by every existing consumer — `userStatedMemoryPrompt.js factText()`, `memory.js memText()`, `memoryLayer.js extractStatementText()` — plus additive, closed structured fields for any future consumer that wants them directly rather than re-parsing text):
  ```
  {
    type: 'preference',
    source: 'user_stated',
    status: 'active',
    confidence: 1,
    payload: {
      key: '<preferenceClass>:<target>',      // e.g. "ACTIVITY_SENTIMENT:ריצה", "TRAINING_TIME_PREFERENCE:EVENING"
      value: '<polarity>',                    // 'POSITIVE' | 'NEGATIVE'
      preferenceClass: '<preferenceClass>',
      polarity: '<polarity>',
      target: '<target>',
      sourceTurnId: '<turnId>'                // traceability only (§18) — never promotes the transcript itself to authority
    }
  }
  ```
- **Persistence Layer**: the existing, unmodified `js/memory.js` CRUD API (`createMemory`/`updateMemory`) — no new Firestore collection, no `firestore.rules` change (client `create`/`update` already permits `source ∈ {user_stated, migrated}` unconditionally on ownership, §5 of the prior investigation).
- **Where the write executes**: at the **application orchestration layer** (`js/app.js` `submitCoachConversationTurn()`), never inside `internalPipelineOrchestrator.js`/`memoryLayer.js` — preserving the Memory Layer's own unmodified, exclusively-read-only role (its header: "אינו כותב דבר") and the existing architectural convention that the Composite Engine computes while `app.js` performs the actual Firestore side effect, exactly as `ConversationRepository.createPending()`/`completeTurn()` already do. The governed pipeline (§9/§10) only ever produces the **Preference Intake Authorization** — never a TerminalDecision, never a write — additively attached to Pass 1's own returned `output` (`output.preferenceIntakeAuthorization`); `app.js` executes the write, and only a confirmed success may trigger the separate, second governed pass that forms an acknowledgment (§13/§14).
- **Consumption**: automatic, with zero new consumer code. Once written `status:'active', source:'user_stated', type:'preference'`, the record is immediately visible to `stateAccess.js readUserStatedMemory()` (if consent remains granted), and therefore to `ActivityPreferenceInterpreter`/`ActivityOppositionInterpreter`/`assembleUserStatedMemoryFragment()`/the D6 sheet — all unmodified.

# 12. Identity / Dedup / Contradiction / Supersession Contract

Deterministic, existing-primitive-based — no new lifecycle system, no `status:'superseded'` usage in V1 (mirrors USM-001's own disclosed non-activation of `superseded`).

- **Deterministic document ID**: `'conv_pref_' + <preferenceClassSlug> + '_' + safeKey(normalizedTarget)`, reusing `js/memory.js`'s own existing, already-exported `safeKey()` helper — the same deterministic-ID convention `migrateIfNeeded()` already uses (`'mig_pref_' + safeKey(k)'`). `normalizedTarget` = the closed token as-is (classes B/C) or the literal activity text lowercased/trimmed (class A, reusing `ActivityPreferenceInterpreter`'s own `normalizeLiteral()` pattern).
- **Existence-and-status check precedes every write** (one additive, narrow read on `js/memory.js`'s own already-exposed CRUD surface, e.g. `FitMeMemory.get(id)`), executed at the same persistence boundary as the write itself (§14) — never inside the read-only governed pipeline. Exactly three outcomes are defined; every other existing `status` value is treated as **PRESENT-OTHER** and fails closed (no write — not expected in practice, since CPI's own `conv_pref_*` ID namespace is never written by any other producer):

  | Existing record at the deterministic ID | Write mode | `status` after write | Distinct acknowledgment required? |
  |---|---|---|---|
  | **Absent** | `createMemory(rec, deterministicId)` | `'active'` | No — ordinary first-capture acknowledgment (§13) |
  | **`status:'active'`** | `updateMemory(deterministicId, {payload, confidence, status:'active'})` (merge) | `'active'` (unchanged) | No — ordinary update acknowledgment (§13); same statement twice or a contradiction both resolve here |
  | **`status:'rejected'`** | `updateMemory(deterministicId, {payload, confidence, status:'active'})` (merge) — **resolves Issue 3 (Canonical Review)** | `'active'` (reactivated) | **Yes — mandatory.** See below. |
  | Any other existing `status` (`superseded`/`archived`/`candidate` — not expected at this ID namespace) | No write | unchanged | N/A — fails closed, treated as a technical no-write case (§16) |

- **Same preference stated twice**: resolves to the *same* deterministic ID, existing `status:'active'` → **update-in-place** (merge: `payload`, `confidence`, `updated_at`), never a second record.
- **Contradictory preference later** (Product's own example: Day 1 "אני לא אוהב לרוץ" → later "בעצם אני כן אוהב לרוץ", with the record still `active` in between): resolves to the *same* deterministic ID → the polarity field flips in place on the *same* record via the same update-in-place path. This is REM-003 §15's own Human Override principle applied directly: *"הצהרתו מחליפה ערך קודם"* — the user's later declaration replaces the earlier value on the same identity, never creating a second, conflicting `active` record.
- **A rejected record is never silently reactivated** (Product's Issue 3 requirement — "user rejection has authority"). The generic update-in-place path above is deliberately **not** applied to a `status:'rejected'` record without an additional, mandatory step: the resulting write is only performed together with a **distinct, mandatory** reactivation acknowledgment — `wasReactivatedFromRejected: true` (§13/§14) — carried in the turn's one final response, whether that response is the standalone `ACKNOWLEDGED_PREFERENCE` outcome or a `secondaryAcknowledgment` woven into a same-turn primary professional/Safety response (§14). Never indistinguishable from an ordinary first-time capture or an ordinary active-record update, and **never silently dropped merely because a primary response also exists that turn** (§14's Unified Finalization guarantees this — resolved as its own dedicated requirement, distinct from the ordinary, ordinary-brief secondary acknowledgment). This satisfies both halves of Product's own requirement:
  1. **User rejection retains authority**: reactivation is never silent — the user is explicitly, honestly told (via the same governed Expression path, §13/§15) that a previous rejection is being overridden by what they just said, the moment it happens — giving them an immediate, natural opportunity to correct that too (via the same D6 surface, §19) if the new statement was itself a mistake.
  2. **A genuinely new explicit correction can eventually replace a rejection — through conversation, not only through Settings**: since every write CPI ever authorizes already passed §10's own full content-authorization gate (interpreter-eligible, literally anchored, non-Safety-vetoed, consented), a fresh statement resolving to a rejected identity is, by construction, already "a genuinely new explicit correction" (REM-003 Path A) — no additional threshold, confirmation count, or new lifecycle state is introduced (Product's own "do not build a new memory lifecycle system" instruction; reuses only the existing `status:'active'`/`'rejected'` values and the existing merge-update primitive).
  - The existing D6 "אישור" (confirm) button remains available and continues to work exactly as it does today for a `rejected` record — this Item adds a second, conversational route to the same existing `'rejected' → 'active'` transition; it does not replace, gate, or alter the manual one.
- **User-driven correction remains fully separate and unaffected**: if the user manually rejects/edits/deletes this record via the D6 sheet, that action uses the existing, unmodified D6 machinery exactly as it already does for any other memory.

# 13. Acknowledgment Semantic Contract

**Resolves Issue 1 (Canonical Review): the governed pipeline never forms an outcome claiming durable capture before that capture has actually, verifiably succeeded.** CPI-001 therefore recognizes two distinct, sequentially-ordered governed artifacts, never conflated:

**A. Preference Intake Authorization** (§10) — the FIRST governed pass's own output. A deterministic, frozen `{authorized, reason, candidateRecord}` object (§10). **It is not a `TerminalDecision`. It is never handed to `ExpressionInputGate`/`ExpressionRenderer`. It never causes Expression to run.** It only authorizes the persistence boundary (§14) to attempt a write. Nothing about it implies, to the user or to any downstream component, that anything has been remembered yet.

**B. Preference Acknowledgment** — represented in the turn's ONE final `TerminalDecision`, formed **only** by a SECOND, bounded, post-persistence governed step (§14, "Unified Finalization") — never by the same pass that produced the Authorization above, and never as a second, competing decision alongside a primary one. It takes exactly one of two mutually-exclusive shapes, chosen deterministically by §14 from a single fact — whether Pass 1's own primary Stage 3-9 flow already produced real content (`kind !== 'SILENCE'`) or not:

- **B.1 — Standalone**: a NEW `TerminalDecision.kind` value, **`ACKNOWLEDGED_PREFERENCE`**, used only when Pass 1's own primary decision was `SILENCE` (nothing else to say this turn). Structurally the fourth non-Candidate construction shape Decision Formation recognizes (after `form()`'s Safety-reviewed path, `formDecisionPassSilence()`'s zero-Candidate path, and DUC-001's `formUnsupportedCapabilityOutcome()`'s own explicit precedent). New Decision Formation function: **`formAcknowledgedPreferenceOutcome(params)`**, structurally identical to `formUnsupportedCapabilityOutcome()`: `{status:'FORMED', decision:{kind:'ACKNOWLEDGED_PREFERENCE', rationale:{preferenceClass, polarity, target, wasReactivatedFromRejected}, decisionPassTrace:{...}, candidateProvenance:[], immutable:true}}` — no `boundaryType`, no `confidence`/`hierarchyTier`, no `safetyDisposition` (no Candidate ever existed; `safetyPort.finalReview()` is never called, exactly as for `SILENCE`/`UNSUPPORTED` today).
- **B.2 — Attached (resolves the Canonical Review's same-turn collision requirement)**: used whenever Pass 1's own primary decision was real content (`RECOMMENDATION`/`INITIATIVE`/`UNSUPPORTED`/a Safety `BOUNDARY`). A NEW, small, **pure, additive** Decision Formation function, **`attachSecondaryAcknowledgment(terminalDecision, ack)`**, returns a new frozen object identical to the input `terminalDecision` in **every existing field** (`kind`, `rationale`, `confidence`, `hierarchyTier`, `boundaryType`, `safetyDisposition`, `modification`, `decisionPassTrace`, `candidateProvenance`, `immutable`) — none of them read, re-derived, or altered — plus exactly one new, optional field: `secondaryAcknowledgment: {preferenceClass, polarity, target, wasReactivatedFromRejected}`. This is a structural copy-plus-one-field operation, never a second decision-forming act: it does not re-invoke `safetyPort.finalReview()`, does not re-evaluate eligibility/evidence/winner-selection, and does not alter the primary decision's own already-Safety-reviewed content in any way — Safety's own output is therefore never weakened, diluted, or reinterpreted by this attachment.

Distinct from:
- **SILENCE** — no Candidate, nothing to say (unchanged meaning; still used when nothing at all was detected AND no preference was authorized/persisted).
- **UNSUPPORTED** — a recognized *request* with no capability to serve it (unchanged meaning; requires `affirmativeRequest.present`, never fires for a bare preference statement) — may itself carry an attached `secondaryAcknowledgment` (B.2).
- **RECOMMENDATION/INITIATIVE/BOUNDARY** — real professional/Safety content, never fabricated, never altered by this Item — may themselves carry an attached `secondaryAcknowledgment` (B.2), which never changes their own `confidence`/`hierarchyTier`/`safetyDisposition`/`boundaryType`/`modification` fields.

`rationale` (B.1) / `secondaryAcknowledgment` (B.2) carry only closed fields (never raw free text) so Expression has something structured to render from. `wasReactivatedFromRejected` (§12) is present in both shapes and lets Expression's own steering instructions (§15) select the mandatory, distinct reactivation acknowledgment wording rather than the ordinary one — content is still entirely Expression's own choice.

**Canonical invariant (governs §14's own control flow, restated for emphasis):**

> **NO SUCCESSFUL DURABLE WRITE → NO Preference Acknowledgment (standalone or attached) → NO acknowledgment content in any Delivery Intent.**

Neither `formAcknowledgedPreferenceOutcome()` nor `attachSecondaryAcknowledgment()` is **structurally reachable** unless the persistence boundary (§14) has already confirmed a successful write and explicitly invokes the second governed pass with the confirmed, persisted record — never speculatively, never before, never independent of that confirmation, and never decided or suppressed by `app.js`/UI code after the fact.

**The reverse implication now DOES hold, by design — resolves the Canonical Review's same-turn collision correction.** A successful Typed Memory write **always** results in the acknowledgment semantic being represented in the turn's one final response — per §14's Unified Finalization, either as the standalone `ACKNOWLEDGED_PREFERENCE` outcome (B.1, when nothing else needed saying) or as a `secondaryAcknowledgment` attached to the SAME turn's real primary content (B.2, when one exists) — never omitted, and never delivered as a second, competing response. The primary professional/Safety semantic always remains structurally untouched and takes priority in ordering/prominence (§15); the acknowledgment is always secondary and brief in the merged case, and always mandatory (never silently suppressed) specifically for a reactivation-from-rejected (§12), in both B.1 and B.2 shapes alike.

# 16. Failure Semantics

No scenario ever claims persistence that did not occur (Product's explicit instruction) — enforced structurally by the two-pass sequencing of §13/§14, not by a presentation-layer suppression. No scenario writes `SILENCE` and later shows/persists an acknowledgment, no turn ever renders/persists two competing assistant responses, and — resolving this round's Canonical Review correction — no successful capture is ever silently dropped merely because a primary response also exists that turn (§14's Unified Finalization).

1. **Preference detected + persisted successfully, no competing primary content** (Pass 1's own `terminalDecision.kind==='SILENCE'`): Pass 1 authorizes and defers rendering (§14 step 5) → the CCC-001 record stays `PENDING` (§14 step 8) → the persistence boundary's write (§11/§12) succeeds → Unified Finalization forms the **standalone** `ACKNOWLEDGED_PREFERENCE` outcome (§13.B.1) → Expression dispatches → `app.js` performs the single, deferred `completeTurn(COMPLETED, assistantText:<acknowledgment>)` and renders it.
2. **Preference detected but `memoryConsent` is false**: §10 gate returns `authorized:false, reason:'CONSENT_ABSENT'` → `preferenceIntakeAuthorization.authorized !== true` → the **existing, unmodified, immediate** CCC-001 lifecycle applies (§14 step 6) — Pass 1's own ordinary outcome (`SILENCE`, or a real Candidate if one independently exists) is rendered and persisted exactly as it always has been, with zero deferral, per Product Decision 11.
3. **Interpretation ambiguous**: interpreter (§9) returns `eligible:false, ineligibleReason:'AMBIGUOUS'` → `authorized` is never even evaluated (no gate invocation) → identical to Scenario 2's existing, unmodified, immediate CCC-001 lifecycle.
4. **Persistence fails technically** (Firestore error after §10 authorized the write): `preferenceIntakeAuthorization.authorized===true` → the CCC-001 record was already correctly held `PENDING` (§14 step 7, never prematurely written) → `app.js` catches the write failure and applies the existing technical-failure handling (`renderNoResponse()`, `showError()`, `ErrorTelemetry.report()` — code only) to the **entire turn** → **no `completeTurn()` call is ever made** — the record remains `PENDING`, never falsely `SILENCE`, regardless of whether Pass 1 had separately computed a real primary response this cycle (§14's own disclosed, Product-directed tradeoff). The user is never told FITME "understood" or "will remember" something that, in fact, was not saved.
5. **Statement outside approved V1 semantic coverage** (e.g. a habit/frequency statement, a food preference): interpreter returns `ineligibleReason:'OUT_OF_V1_SCOPE'` → identical to Scenario 2/3's existing, unmodified, immediate CCC-001 lifecycle. Per Product's own instruction, this may remain ordinary conversation behavior until a future, broader capability exists.
6. **Statement is Safety-relevant and the interpreter (§9) itself correctly excludes it**: interpreter returns `ineligibleReason:'SAFETY_EXCLUDED'` → identical to Scenario 2/3/5's existing, unmodified, immediate CCC-001 lifecycle — this path never engages, never overlaps with, and never substitutes for real Safety detection.
7. **Statement is Safety-relevant but the interpreter (§9) incorrectly returns `eligible:true`** (resolves Issue 2, Canonical Review): the deterministic gate's own independent Safety veto (§10 point 5) catches this regardless — `SafetyContextInterpreter`, invoked independently on the same current-turn text via `classifyWithStatus()`, finds a restriction → gate returns `authorized:false, reason:'SAFETY_VETO'` (or `'SAFETY_VETO_DURABLE'`) → identical to Scenario 2/3/5/6's existing, unmodified, immediate CCC-001 lifecycle. A single misclassification by the preference interpreter alone can never result in a Safety-relevant statement being persisted as an ordinary preference.
8. **A repeated/contradicting statement resolves to a `status:'rejected'` record** (resolves Issue 3, Canonical Review): authorization proceeds normally (§10) if content-valid/consented/non-Safety-vetoed; at the persistence boundary, the existence-and-status check (§12) identifies the existing record as `rejected` → the write reactivates it (`status:'active'`) **only together with** a `wasReactivatedFromRejected:true` Preference Acknowledgment — standalone (§13.B.1) or attached to a same-turn primary response (§13.B.2), whichever shape Unified Finalization selects — the single, deferred `completeTurn(COMPLETED, assistantText:<that one response>)` follows the same sequencing as Scenario 1 — never the ordinary, indistinguishable acknowledgment wording, and never silent, **and never dropped even when a primary response exists this turn** (see Scenario 10).

No write, no Unified Finalization, no acknowledgment — the turn behaves exactly as if the statement had never been classified as a preference at all.

Safety is never suppressed or weakened (its own fields are copied through untouched); a real professional response is never overwritten, replaced, or diluted by the acknowledgment; the preference is never silently captured-but-unacknowledged; exactly one response is rendered and persisted — never two, never zero.

# 17. Safety Boundary

CPI-001 never has Safety authority and never competes with it:
- `ExplicitPreferenceStatementInterpreter`'s own prompt explicitly excludes anything resembling a medical/practitioner-sourced restriction (§9), mirroring `ActivityOppositionInterpreter`'s own already-approved instruction: *"a Safety restriction... is never opposition — classify it as NOT_OPPOSITION here regardless of content."* This is a first-line, advisory signal only (§9) — never, by itself, sufficient authorization (§10).
- **Resolves Issue 2 (Canonical Review)**: an independent, fail-closed Safety veto (§10 point 5) sits between this interpreter's own judgment and any authoritative write. It reuses `SafetyContextInterpreter` (USC-001) — the exact same, existing, already-production-configured (`js/app.js:325`) collaborator `memoryLayer.js`'s own `userSafetyContext` step already calls for durable memory — applied additively to the current turn's own text, using the same `'turn:' + turnId` submission convention DUC-001 already established for `explicitRequestControls`/`readinessStateContext`. This is **not** a second Safety architecture: no new interpreter, no new prompt, no new classification vocabulary — one more record handed to a collaborator that already exists, already runs in production, and already owns exactly this judgment ("does this text literally, unambiguously express a Safety restriction?"). A secondary, zero-cost check against the already-assembled `pipelineContext.userSafetyContext.items` (durable restrictions from prior turns) adds defense in depth at no additional read/AI cost.
- **Safety fail-closed clarification (Canonical Review)**: the veto's authoritative signal comes from a small, purely additive `classifyWithStatus()` export on `safetyContextInterpreter.js` (§10 point 5) — `classify()` itself, its existing return contract, and its existing sole caller (`memoryLayer.js`) are untouched. A classifier failure (throw/timeout/malformed output) is never silently treated as "no restriction" — it fails closed to `authorized:false, reason:'SAFETY_VETO_UNAVAILABLE'` (§16, Scenario 9). This still creates no Safety Intake and persists no Safety information — it only ever prevents an authoritative CPI write when the mandatory veto could not be evaluated reliably; the statement's own content is left exactly as unrecognized as any other vetoed statement (below).
- CPI-001 creates no Safety Context, persists no Safety information, performs no diagnosis, and routes nothing to a new or existing Safety capability — the veto is a pure, non-persisted refusal signal (§10); a vetoed statement's content is not captured, stored, or forwarded anywhere by this Item.
- The reuse in §10 is a one-directional call OUT to `SafetyContextInterpreter`, never the reverse — no output of this Item's new components is ever read by `SafetyContextInterpreter`, `UserSafetyProvenanceInterpreter`, `SafetyLayer`, or any Canonical Safety Rule, and no new dependency is introduced on `UserSafetyProvenanceInterpreter`, `SafetyLayer`, or Canonical Safety Rule matching.
- Safety review (`safetyPort.finalReview()`) is never invoked for `ACKNOWLEDGED_PREFERENCE` (no Candidate exists), exactly matching `SILENCE`/`UNSUPPORTED`'s own existing, already-approved non-Safety-reviewed shape — this is not a new Safety bypass, it is the same pre-existing shape those two kinds already have. The §10 veto is a strictly additional, stricter refusal layer that exists precisely because this path is not Safety-reviewed — never a substitute for `finalReview()`, never a claim that this path has been "cleared" by Safety in the way a real Candidate would be.
- A statement that is Safety-excluded (§9) or Safety-vetoed (§10/§16 Scenario 6/7) is **not** thereby captured, routed, or handled by Safety either — it is simply left exactly as unrecognized as it is today (Investigation 1's own finding: no live Safety-intake channel from conversation exists yet); this Item neither creates nor closes that gap, consistent with "Friends Alpha Item 6 — bare-statement handling + natural Safety-information intake, NOT STARTED" remaining a separate, later Item.
